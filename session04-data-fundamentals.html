Why this matters for ML

A surrogate model learns output = f(inputs) from examples.

  • it can only be as good as the data: range, density, errors, units
  • most of the time in a real ML project goes into data, not models
  • Modules 1–2 give you the tools; Module 3 builds on them

What is a dataset?

Rows and columns

run_id thickness_mm fillet_radius_mm load_N E_GPa max_stress_MPa deflection_mm safety_factor
R001 17.3 6.5 1537 199.4 170.4 0.502 2.083
R002 13.3 1.9 2332 195.2 527.5 1.714 0.673
R003 18.3 4.8 2729 190.9 297.9 0.787 1.192
  • row = one observation = one calculation run
  • column = one variable, one unit, one type
  • ID column — to trace a row back to the calculation that produced it

Inputs and outputs

Inputs — you choose them

  • thickness t
  • fillet radius r
  • load F
  • modulus E

In ML: features, X

Outputs — the solver computes them

  • max stress
  • deflection
  • safety factor

In ML: targets, y

Safety factor = 355 / max stress. It is derived from another output, so it adds no new information. Knowing which columns are derived avoids surprises later (data leakage, Module 3).

Types of variables

Type Examples What you can do
continuous thickness, stress, temperature any arithmetic
discrete (count) number of bolts, mesh elements counts, sums
categorical material grade, solver status count, group
ordinal mesh quality: coarse < medium < fine order, but no distances
identifier run_id trace, join — never compute
date / time time of calculation sort, durations

Units and scales

  • the same column must have one unit for all rows
  • engineering quantities have very different scales:
Variable Typical range
fillet radius 1 – 8 mm
load 200 – 3000 N
modulus E 190 000 – 210 000 MPa
  • many ML methods are sensitive to scales → normalisation (Modules 3–4)
  • unit mistakes (N vs kN, MPa vs Pa) are the most common data error — Session 7

File formats

Format Looks like Notes
CSV 12.5,4.0,1500 plain text, universal; separator and decimal sign vary
Excel .xlsx spreadsheet fine for small tables; watch merged cells and formatting
JSON {"t": 12.5, ...} nested data, configs, web APIs
HDF5 / NPZ / Parquet binary large arrays, fields, fast
solver formats (VTK, .rst, .odb) binary result fields; usually exported first

European locale exports often use ; as separator and , as decimal sign. We will handle it.

Scalar results vs fields

  • scalar results — one number per run: max stress, deflection → one row per run
  • fields — a value at every node: stress distribution → one array per run
run R001:  node 1  node 2  ...  node 25 000
           112.3   118.9         0.4      (MPa)

Modules 1–2 work with scalar tables. Fields come back in Module 4.

Planning a series of calculations

How do we choose the inputs?

Each calculation costs time. Which points of the design space should we compute?

  • full factorial grid — every combination of a few levels per input
  • random sampling — uniform random values in each range
  • Latin hypercube (LHS) — random, but each input’s range is evenly covered

Full factorial grid

from itertools import product

thickness = [8, 12, 16, 20]
radius = [1, 4, 8]
load = [500, 1500, 3000]

grid = list(product(thickness, radius, load))
print(len(grid), "runs")
print(grid[:4])
36 runs
[(8, 1, 500), (8, 1, 1500), (8, 1, 3000), (8, 4, 500)]

4 inputs × 10 levels = 10 000 runs. Grids grow exponentially with the number of inputs (“curse of dimensionality”). Fine for 2–3 inputs, too expensive beyond that.

Random and Latin hypercube sampling

LHS: every one of the 16 columns and 16 rows contains exactly one point — good coverage with few runs.

Practical rules for a calculation plan

  • define the domain of applicability first: min and max of every input
  • include the corners and the centre (extremes are where models fail)
  • record everything: inputs, solver version, mesh, status, date
  • keep some runs aside for testing (Module 3)
  • automate: the plan is a table; the solver reads it and writes results in a table

First look at the course data

Reading a CSV with the standard library

import csv

with open("data/bracket.csv") as f:
    rows = list(csv.DictReader(f))

print(len(rows), "rows")
print(rows[0])
300 rows
{'run_id': 'R001', 'thickness_mm': '17.3', 'fillet_radius_mm': '6.5', 'load_N': '1537.0', 'E_GPa': '199.4', 'max_stress_MPa': '170.4', 'deflection_mm': '0.502', 'safety_factor': '2.083'}
  • each row is a dictionary, every value is a string
  • in Colab: upload the file, or read it from the course site (see the Data page)

Computing statistics by hand

stress = [float(r["max_stress_MPa"]) for r in rows]
n = len(stress)
mean = sum(stress) / n
std = (sum((s - mean) ** 2 for s in stress) / (n - 1)) ** 0.5
failed = sum(1 for r in rows if float(r["safety_factor"]) < 1)

print(f"mean {mean:.1f} MPa, std {std:.1f}, min {min(stress)}, max {max(stress)}")
print(f"{failed} of {n} runs exceed yield ({failed / n:.0%})")
mean 357.3 MPa, std 277.6, min 23.6, max 1443.1
118 of 300 runs exceed yield (39%)

It works — but it is a lot of typing for simple questions. Next sessions: NumPy and pandas do this in one line each.

Summary

  • dataset = table: row = run, column = variable with one unit and type
  • inputs (features X) vs outputs (targets y); know which columns are derived
  • variable types decide what operations make sense
  • CSV is the common format; separators and decimal signs vary
  • plan calculations: grid for few inputs, LHS for more; cover the extremes
